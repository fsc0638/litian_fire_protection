# 部署與自動部署

主機以 GitHub clone 部署；推上 main 後自動測試、通過才部署。腳本說明另見 `deploy/oracle/README.md`。

← 回到 [專案介紹](../README.md)

## 部署

主機上以 GitHub clone 部署（2026-10-01 起）：

```
# 第一次
git clone https://github.com/fsc0638/litian_fire_protection.git /opt/litian/repo
# 手動更新（備份資料庫 → git pull → 同步部署檔 → 重建 api → 重載法規庫 → 健康檢查）
bash /opt/litian/repo/deploy/oracle/06_update_from_git.sh
# 啟用自動部署（只需一次）
bash /opt/litian/repo/deploy/oracle/11_install_autodeploy.sh
```

**自動部署**（2026-10-05 起）：推上 GitHub `main` 後約 2～3 分鐘內，主機自己發現新提交 → 在拋棄式容器裡用新版程式跑全部測試（含資料庫整合測試；測試用專屬的資料庫帳號，碰不到正式資料）→ 通過才部署那一個提交（部署前自動備份資料庫）。主機上的指令一律不要加 `sudo`。

- 測試沒過：不部署，網站維持原版本；修好後再推一次就會重試。測試環境本身出錯（不是測試沒過）會自動重試，連續 3 次才暫停。
- 部署後健康檢查不過（含背景服務一直重啟），或部署途中被中斷（逾時、重開機）：程式與映像自動換回前一版，並**暫停自動部署**；處理後執行 `bash /opt/litian/repo/deploy/oracle/10_autodeploy.sh resume`，會重新測試並部署。注意：換回的是程式與映像，資料庫結構變更不會自動還原（需要時用 `/opt/litian/backup/` 裡部署前的備份）。
- 健康檢查通過、只有後續的法規庫重載失敗：保留新版，紀錄裡會有警告，手動重跑即可。
- 看狀態與最近紀錄：`bash /opt/litian/repo/deploy/oracle/10_autodeploy.sh status`；要手動維護時先 `pause`。紀錄在主機 `/opt/litian/autodeploy/`。目前沒有推播通知，暫停時只看得到狀態。
- `main` 的歷史被改寫（強制推送）時會暫停。處理方式：`git -C /opt/litian/repo fetch origin && git -C /opt/litian/repo reset --hard "$(git -C /opt/litian/repo merge-base HEAD origin/main)"` 再 `resume`（新的 main 會先測試再部署；不要直接 reset 到 origin/main 再手動部署，那樣會跳過測試）。
- 磁碟剩不到 6 GB 時整輪略過，清出空間後自動繼續；舊映像用 ID 清除，不使用整台清除的 `docker system/builder prune`（只清本系統自己的，見「磁碟空間」）。
- 做法是主機定時讀取公開 repo，不需要金鑰或 webhook，GitHub 端不用設定。**能推上 `main` 就等於能在主機上以可 sudo 的身分執行程式**（新版的部署腳本會在主機執行；主機上的資料與 `.env` 金鑰都在範圍內），所以 `main` 的分支保護必須維持：只能經負責人核准的 PR 合併、禁止強制推送。

## 磁碟空間

磁碟滿了資料庫就寫不進去，整個網站會停擺。系統自己的防護：

- 上傳：剩餘空間扣掉這次上傳大小的兩倍（上傳內容先整份存進暫存區、再複製到案件資料夾）後低於 3 GB 就拒收（工作台顯示「伺服器磁碟空間不足…」）；一次上傳合計上限 1 GB、單檔 200 MB。登入、大小、空間都在讀上傳內容之前檢查，被拒的請求不會先存進暫存區；沒帶大小的請求（瀏覽器不會這樣送）空間照 1 GB 算，讀到超過 1 GB 就中止。其他網址一律不收附檔案的表單（415）。
- 剩不到 8 GB 時，管理者打開工作台會在頂端看到提醒。自動部署剩不到 6 GB 時暫停（見上）。
- 這兩個門檻（3 GB、8 GB）是固定的：在 `.env` 設 `UPLOAD_MIN_FREE_GB`、`DISK_WARN_GB` 不會生效（`docker-compose.yml` 沒有把它們傳進 api 容器）。空間不夠時照下面清理，不要調低門檻。
- 映像分層：第三方套件只在 `pyproject.toml` 改了才重裝。以前每次部署都重裝全部套件，多留約 600 MB 的建置快取；現在平常改程式的部署只多幾 MB，每改一次 `pyproject.toml` 約多 600 MB（改過之後照下面清）。
  - 套件版本固定在重裝當時，之後的部署不會自動升級。要更新（例如安全修正），提高 `pyproject.toml` 裡該套件的版本下限：自動部署會先建候選映像、跑完測試才部署。
  - 手動執行 `06_update_from_git.sh` 或 `10_autodeploy.sh run` 前先執行 `umask 022`（計時器已這樣設定）：`pyproject.toml` 的檔案權限不同，Docker 會當成改過，再裝一次全部套件。

查看：

```
df -h /opt/litian /var/lib/docker              # 剩餘空間
sudo docker system df                           # 映像、容器、建置快取各占多少
sudo docker buildx du --verbose | less          # 建置快取逐筆：ID、Size、Description（哪個建置步驟）、Shared（還被映像使用）
```

只清本系統的舊建置快取（這一版部署之後、以及每次 `pyproject.toml` 改過並部署之後再做：前一份套件安裝層從此不再使用）。一筆一筆用 ID 刪，不要用 `docker system prune`、不加篩選的 `docker builder prune`／`docker buildx prune` 這類全部清掉的指令：會把還要用的映像與快取一起刪，也無法事先看清楚刪了什麼。

第 1 步：列出要清的。

```
# 本系統舊的套件安裝層，連同疊在它上面的層（上面的層要先刪，下面那層才刪得掉），最上層排最前面。
# 認定方式：建置步驟是套件安裝（現在的「pip install --no-cache-dir -r /tmp/requirements.txt」或舊 Dockerfile 的
# 「pip install --no-cache-dir .」），而且底下有本系統安裝中文字型（fonts-noto-cjk）的那一層。
# 還被映像使用的（Shared: true，包括目前在跑的這一版）不列：刪不掉，也不該刪
sudo docker buildx du --verbose | awk -v RS= '
  function up(x,  p) { p = parent[x]; sub(/^,/, "", p); sub(/,.*/, "", p); return p }
  function ours(x,  a, k) {
    if (desc[x] !~ /pip install --no-cache-dir (\.|-r \/tmp\/requirements\.txt)/) return 0
    for (a = up(x); a != "" && k < 100; a = up(a)) { if (desc[a] ~ /fonts-noto-cjk/) return 1; k++ }
    return 0 }
  { id = ""; par = ""; sh = ""
    for (i = 1; i <= NF; i++) {
      if ($i == "ID:") id = $(i + 1)
      else if ($i == "Shared:") sh = $(i + 1)
      else if ($i == "Parent:") par = $(i + 1)
      else if ($i == "Parents:") for (j = i + 1; $j == "-"; j += 2) par = par "," $(j + 1) }
    desc[id] = $0; parent[id] = par; shared[id] = sh }
  END { for (id in desc) { if (shared[id] == "true") continue; d = 0
          for (a = id; a != "" && d < 100; a = up(a)) { if (ours(a)) { print d, id; break }; d++ } } }' \
  | sort -rn | cut -d' ' -f2 >/tmp/litian-old-cache.txt
wc -l </tmp/litian-old-cache.txt
```

第 2 步：先刪一筆確認。先記下總筆數、看這一筆：

```
id=$(head -n 1 /tmp/litian-old-cache.txt)
sudo docker buildx du --verbose | grep -c '^ID:'
sudo docker buildx du --verbose | awk -v RS= -v id="$id" '$2 == id'
```

Description 是本系統的建置步驟，再單獨執行這一行（會問 y/N，回答 y）：

```
sudo docker buildx prune --filter id="$id"
```

確認刪掉了：

```
sudo docker buildx du --verbose | grep -c '^ID:'      # 比剛才少 1
sudo docker buildx du --verbose | grep -c "$id"       # 0＝已刪
```

第 3 步：上面兩個數字都對，再照清單順序刪其餘（順序不能亂），最後看剩餘空間：

```
tail -n +2 /tmp/litian-old-cache.txt | while read -r id; do sudo docker buildx prune -f --filter id="$id" | tail -n 1; done
df -h /var/lib/docker
```

- 第 1 步 0 筆：通常是沒有可清的。`docker buildx du` 明明還有本系統的大筆快取時，先看輸出格式是不是不一樣，再逐筆核對 ID；不要改用沒有篩選的清除指令。
- ID 要完整（篩選是比對字串，太短會比對到別筆）。不要加 `--all`：不加時，還被映像使用的快取會自動略過（目前在跑的那一版要等下次部署後才清得掉）。
- `prune` 回報 `Total: 0B`：那筆還被映像使用，沒有刪。用 `sudo docker images --filter dangling=true` 看有沒有沒標籤的舊映像；`sudo docker history --no-trunc 映像ID | grep -c fonts-noto-cjk` 大於 0 才是本系統的，用 `sudo docker rmi 映像ID` 刪掉後從第 1 步重來。
- 平常改程式的部署只多幾 MB（程式與資料的小層），不必常清；`pyproject.toml` 改過並部署之後清一次。

## 轉檔器升級後：全部重新處理

轉檔器（LibreDWG）修正或升級後，舊的轉檔結果可能夾帶錯誤內容（例：0.14 套上游修正 #1416 之前，含換行的文字後面會接上亂碼）。

開始前：

- 建議暫停自動部署：`bash /opt/litian/repo/deploy/oracle/10_autodeploy.sh pause`，全部跑完再 `bash /opt/litian/repo/deploy/oracle/10_autodeploy.sh resume`。部署會重啟 worker，處理到一半的大檔要從頭來（退回排隊、不算失敗次數）。
- 從工作台匯出各案件的報告留存。審核決定是照缺失的識別碼（規則、樓層、房名、位置或設備名、標註文字）對應的：房名、標註文字原本夾帶亂碼的缺失，重跑後識別碼會變、回到未審核（舊的決定還在資料庫，只是對不上），要請審核人員重看。
- 等 worker 閒著再執行（沒有排隊、處理中、畫原圖中，查法見下面「看進度」）：worker 正在處理這些案件的檔時 reprocess 不會動；畫原圖和抽取大檔同時跑也可能記憶體不足，失敗的檔不會自動重試。
- 確認磁碟空間：舊的轉檔結果不刪，移到各案件資料夾的 `.pre-reprocess/<執行時間>/`，重跑又會產生差不多大的新檔。試跑的「合計」那行列出舊轉檔結果的總大小，`df -h /opt/litian` 的剩餘空間要比它多（自動部署另外要留 6 GB）。

新版部署好後在主機上執行：

```
cd /opt/litian
sudo docker compose exec -T worker python -m litian.drawing.cli reprocess --all --dry-run   # 先看會做什麼，不動任何東西
sudo docker compose exec -T worker python -m litian.drawing.cli reprocess --all             # 或 --case 案件ID（可重複）
```

- 每個 DWG／DXF 都完整重跑：DWG 重新轉檔、重新綁定外部參考、重新抽取、重新檢核，有樓層圖的重畫 CAD 原樣圖。移走的只有 worker 產生的 `.converted.dxf`、`.bound.dxf`：不刪，移到 `data/cases/<案件ID>/.pre-reprocess/<執行時間>/`（報告逐案列出，worker 不會用到），上傳的原檔不動；舊結果在工作台照常顯示，重跑到該檔時才更新。
- worker 正在處理這些案件的檔（處理中、檢核中）時，整個不動，印出「worker 正在處理：…，沒有任何更動，等它處理完再執行一次」、結束碼 1：等它處理完（`… cli status 案件ID` 看狀態）再執行同一個指令。試跑也會列出這些檔（「worker 正在處理，正式執行會停下」）。
- 有轉檔結果移不走（權限不足等）時，會在移任何檔之前停下；試跑也會列出來。
- 上傳的原檔不見了的檔不動（轉檔結果是僅存的圖），上次把它綁成外部參考的主圖也不動（重跑會綁不到）；報告列在「略過」。
- 看進度：`sudo docker compose exec -T postgres psql -U litian -d litian -c "SELECT status, count(*) FROM case_file GROUP BY 1" -c "SELECT cad_state, count(*) FROM case_file WHERE cad_state IN ('pending', 'rendering') GROUP BY 1"`。沒有 queued、processing、reviewing，也沒有 pending、rendering，就是全部完成。單一案件用 `… cli status 案件ID`。worker 一次處理一個檔，排隊的檔都處理完才開始畫原圖，整批可能要一兩個小時以上。failed 的檔看 error 欄，不會自動重試。
- 執行一次就好（中途中斷或出錯才再執行）：再執行會把已經重跑完的檔又排一次（轉檔結果再移一份到新的 `.pre-reprocess/<執行時間>/`）。

新版轉不了某個 DWG（`… cli status 案件ID` 顯示 failed，錯誤是轉檔失敗或等待轉檔逾時）時，可以把舊的轉檔結果搬回來用（內容是舊版轉的，帶著舊的錯誤）：

```
cd /opt/litian
# 1. 搬回原處（有 存檔名主體.bound.dxf 也一起搬）。存檔名＝案件資料夾裡的檔名，例 001_Area_1F.dwg；主體＝001_Area_1F
sudo mv data/cases/案件ID/.pre-reprocess/執行時間/存檔名主體.converted.dxf data/cases/案件ID/
# 2. 它是別的圖的外部參考時：先重跑的主圖綁不到它（記「存檔名（尚未轉檔）」），把這些主圖排回完整重跑
sudo docker compose exec -T postgres psql -U litian -d litian -c "UPDATE case_file SET status = 'queued', review_only = false, attempts = 0 WHERE case_id = 案件ID AND status IN ('done', 'failed') AND stats->'xref'->'failed' ? '存檔名（尚未轉檔）'"
```

- 這個檔自己維持 failed（綁定外部參考看到轉檔結果就直接用，不會再送轉檔）。第 2 步不要改用 reprocess：它會把搬回來的檔又移走。
- 全部完成、確認沒有要搬回來的檔之後，刪掉舊的轉檔結果釋放空間：`sudo rm -rf /opt/litian/data/cases/*/.pre-reprocess`。

對外：`https://<SITE_ADDRESS>/api/...`（sslip.io 測試網址常被企業網路攔截，正式期要換自己的網域）。
